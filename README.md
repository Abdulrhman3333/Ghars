# غَرْس · Ghars

An Arabic-first (RTL) platform for learning to recite the Quran correctly, practically and theoretically, organized **by juz'**. Learners who pass the exam for a juz' become teachers for that juz' automatically, which grows a lineage tree.

> Ghars certificates («شهادة غرس») are **not** an official ijaza. The label lives in one constant: `CERTIFICATE_LABEL` in `src/lib/config.ts`.

## Stack

- Next.js 15 (App Router) · TypeScript (strict) · Tailwind CSS 4 · RTL throughout
- Supabase: PostgreSQL, Auth, Storage, Row Level Security on every table
- Quran text: a local snapshot of the Madani mushaf (quran.com API v4), rendered with QCF v2 page fonts
- Deployment target: Vercel

## Project layout

```

  migrations/      schema, state machines, RLS, views, functions (apply in order)
  seed.sql         reference data: error types, sub-types, categories, admin bootstrap notes

    validation/    zod schemas
  messages/ar.json all UI copy
tests/unit/        Vitest suites for layout, mark planning, validation
scripts/snapshot-quran.mjs
```

## Setup

### 1. Requirements

- Node.js 20 or newer
- A Supabase project (hosted, or the Supabase CLI for local development)

### 2. Environment variables

Copy `.env.example` to `.env.local` and fill in:

| Variable | Where to find it |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase dashboard → Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Same page (anon public key) |

The service-role key is **not** used by the app. Keep it out of the repository.

### 3. Database

Apply the migrations in filename order (the Supabase CLI does this with `supabase db push`). Then load the reference data and the Quran snapshot:

```bash
supabase db push                       # or run supabase/migrations/*.sql in order
# run supabase/seed.sql in the SQL editor (or psql)
# run supabase/seed/quran_snapshot.sql  (≈5 MB; too large for the CLI seed step)
```

To regenerate the Quran snapshot from quran.com: `npm run snapshot:quran`.

### 4. First admin

1. Register your account through the app and confirm the e-mail if confirmations are enabled.
2. In the SQL editor run:

   ```sql
   select public.grant_role_by_email('you@example.com', 'admin');
   ```

   The first admin grant needs no existing admin. After that, only admins can grant roles, and they do it from `/admin/users`.

### 5. Run it

```bash
npm install
npm run dev
```

## Testing

Three layers:

| Layer | Command | What it covers |
| --- | --- | --- |
| Unit | `npm test` | Mushaf layout model, mark planners, validation |
| Database | `npm run test:db` (needs `DATABASE_URL`) | State machines, RLS privacy, sessions and repeat counts, invites, function privileges. Runs in one transaction and rolls back. |
| End-to-end | `npm run test:e2e` | Real browser flows: auth, profile, Mushaf marking, a two-account recitation session, admin access |

**Local walkthrough**

1. Start the app: `npm run dev` (or build and `npm start`). The app uses the project in `.env.local`.
2. In another terminal, run `npm run test:e2e`. The test accounts are in `.env.test.local` (gitignored). Change their passwords after first use.
3. Sign in yourself as `GHARS_ADMIN_EMAIL` to try the admin dashboard, and as the student and teacher to try the flows.

**Cleanup after the session test:** each run leaves one accepted test session between the student and teacher accounts. To remove the test data:

```sql
delete from public.mushaf_sessions
where reciter_id = (select id from public.users where email = 'ghars.teacher@example.com')
  and listener_id = (select id from public.users where email = 'ghars.student@example.com');
```

Use a separate Supabase project for testing before any real users join. The end-to-end tests write to whatever project `.env.local` points to.

## Business rules (where they are enforced)

| Rule | Enforced in |
| --- | --- |
| Teacher status is derived (`progress.state = 'passed'`), never a role | `v_teacher_eligibility`, `nominate_for_exam()` |
| Progress and exam state machines | `*_allowed_transitions` tables + guard triggers (migrations 0003, 0004) |
| Lineage edge = nominating teacher of the passed attempt | `exams.nominated_by`, `get_lineage_tree()` |
| An error targets one word or letters in one word; Bismillah (1:1) is not markable | `quran_words` FK, `guard_error_insert` trigger |
| Subtype must belong to its type | composite FK `mushaf_errors → error_subtypes` |
| Repeat count = same word and type across distinct **accepted** sessions | `v_error_repeat_counts` |
| Email/phone visibility | `users_select_related` policy (migrations 0006, 0008) |
| Auto-assignment: least-loaded certified teacher | `auto_assign_teacher()` (migration 0009) |
| Audio type and size limits | bucket configuration (migration 0005) and server actions |

## Known limitations

- **Invite links** redirect through login and do not return to the invite afterwards; the user reopens the link.
- **Session range** (start/end position) is in the schema but not in the UI yet.
- **Common-error review** approves or rejects but does not edit the entry before publishing, and the review page does not play the submitted audio yet.
- **Email notifications** are not wired yet; in-app notifications are written to `notifications`.
- **Integration tests** for the database functions (session acceptance, RLS matrix, state machines) need a local Supabase instance and are not included yet.
- Age-range matching is stored in the schema but not implemented (by design).

## Windows note

Tooling (Next.js file tracing, Vite) fails when the project path contains `#`. Rename the folder (for example `1-Tahfeed`) before running `npm run build` or `npm test` on Windows.

## Deployment (Vercel)

1. Import the repository and set the two `NEXT_PUBLIC_SUPABASE_*` variables.
2. Make sure the migrations and seed files have been applied to the target Supabase project.
3. Deploy. The middleware refreshes sessions and protects the authenticated routes.
